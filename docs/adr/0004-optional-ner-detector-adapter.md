# ADR 0004: An optional NER detector adapter, and async detectors

- Status: Accepted
- Date: 2026-10-14

## Context

The regex detectors only find a person when a cue marks the name: a label (`Claimant:`), a title (`Ms.`), a schema hint, or an earlier cued mention that propagation can follow. Adjuster notes are full of names with no cue, often typed in lowercase: "spoke with jordan ellery at the body shop". This was a documented gap ("needs NER").

Closing it needs a named-entity model, and pii-gate can't ship one. Its core has zero runtime dependencies and runs in the browser, and NER means a model file, a runtime, or a network service. What pii-gate can do is define how a model the application already runs plugs in, and make sure its output gets the same treatment as everything else.

Two things got in the way:

1. **`Detector` is synchronous.** `mask()` is synchronous and fast (~0.07 ms on a 2 KB note), and most users only run regex. Real NER is almost always async: transformers.js inference, a spaCy or cloud NER call over HTTP, or an LLM. The documented workaround was to call the model yourself and pass its spans in through `staticDetector()`. That doesn't work with `wrapAnthropic`, which collects the strings inside the request itself.
2. **Model output is untrusted input to the masker.** Offsets can be off by one, be counted in code points rather than UTF-16 units, cover half a word, run past the text, or carry a label nobody mapped. If a span is wrong, either part of a name gets through or a policy number gets masked.

## Decision

### Async detectors alongside the sync API

- New type `AsyncDetector`: the same as `Detector`, except that `detect` may return `PromiseLike<Finding[]>`. Every `Detector` is an `AsyncDetector`.
- New functions `maskAsync(text, options)` and `maskAllAsync(texts, options)`, whose options are `MaskAsyncOptions` (`MaskOptions` with `detectors: readonly AsyncDetector[]`). Detection for every text and every detector runs concurrently and finishes **before** anything is replaced. After that they run the same code as the sync path (shared `analyze` → propagation → block check → `applyFindings`), so `maskAll`'s guarantees still hold: a block anywhere aborts before any token is issued, and a name found in one text is propagated to the others.
- `wrapAnthropic` accepts async detectors in `detectors`. It was already async, so it now always masks through the async path.
- **The sync API is unchanged.** `mask`/`maskAll` keep their signatures and code path. Their only new step is a check that each detector returned an array. A detector that returns a promise gets a `TypeError` naming the detector and pointing to `maskAsync`. Before, it failed later with a confusing "Invalid PII category" error.
- **No overhead for regex-only users of the async path.** When no detector returns a thenable, `maskAsync`/`maskAllAsync`/`wrapAnthropic` skip the `Promise.all` and go straight to the shared analysis. A test checks that `maskAllAsync` equals `maskAll` on every golden fixture (masked text, findings, vault entries), and `npm run bench` shows `mask`, `maskAll` and the wrapped call within run-to-run noise of the published numbers.

### The adapter: `nerDetector({ recognize, ... })`

`recognize(text, { signal })` calls the application's model and returns `NerEntity[]`: `{ label, score?, start?, end?, word? }`.

- **Spans.** `start`/`end` are UTF-16 offsets with `end` exclusive. A span is used when its bounds are valid integers and, if `word` is also given, it reads as `word` under a loose comparison: NFKD, combining marks removed, case folded, whitespace and punctuation ignored. So "jose nunez" from an uncased model matches "José Núñez", WordPiece's detokenised "Jean - Luc Moreau" matches "Jean-Luc Moreau", "O'Brien" matches "O’Brien", and NFD text matches an NFC word. Otherwise `word` is searched for, and every whole-word occurrence is reported, which recovers code-point offsets from Python services after an emoji. This search is deliberately looser than propagation (see Word search): it ignores accents and allows a hyphen, apostrophe or period between tokens. So it can mask a variant that propagation of the same value would not, such as "Jose Nunez" for the word "José Núñez". Each variant is masked as found, and restores to its own spelling. If the word is nowhere in the text (a detokenisation the comparison can't undo), the offsets are used after all, since dropping the entity would leak the name. Word-only output, which some transformers.js versions produce, works the same way.
- **Word search.** No regex is ever built from model output. The text is tokenised once, only when some entity needs a search. A token is a run of letters, marks, digits and `_`; in scripts written without spaces (Han, Hiragana, Katakana, Thai, Lao, Khmer, Myanmar, Tibetan) each character is a token. A word matches consecutive text tokens with the same loose keys, where the text between two tokens looks like a gap inside a name: up to four spaces, or one hyphen, apostrophe or period with optional spaces. A comma never matches, so the word "Ana Ruiz" doesn't match "Ana, Ruiz". Each word is anchored on its rarest token, so "de la Cruz" in a Spanish document with thousands of "de" costs only the occurrences of "cruz".
- **Tokenizer pieces.** A `word` starting with `##` (WordPiece continuation) or `Ġ` (byte-level BPE) is rejected as a word, and the entity's offsets are used if it has them (grown to the whole word, so `##son` at the offsets of "Johnson" masks "Johnson"). Without offsets the entity is dropped. Searching for it was the alternative, and `##son` trimmed to "son" would mask every "son" while "Johnson" leaked. A SentencePiece `▁` reads as a space. Word-only, un-aggregated token output (`B-PER "John"`, `I-PER "##son"`) can't be repaired: join the pieces before returning them, as `examples/ner.ts` does. The cost is that Maltese names spelled with `Ġ` are dropped when they come without offsets.
- **Bounded work and size.** Model output is untrusted, and a recognizer that tags every token of a long document must not take the gateway down. (An adversarial review measured 2,000 word-only entities × 2,000 occurrences at 626 ms / 425 MB before these rules. At 50,000 × 5,000 the process was OOM-killed.) So:
  - Duplicate entities are expanded once, and are skipped before any normalisation runs. Offsets spanning more than 256 characters are ignored before the text is sliced. Without this, 20,000 identical whole-text entities on 200 KB spent 9 s in NFKD; now it takes about 10 ms. A word search is keyed by (label, prefix, word) whatever the offsets, so 400 mentions with code-point offsets don't each re-add all 400 hits.
  - Hard caps per result: 100,000 entities, 10,000 spans from word searches and 100,000 candidate positions examined. Offset spans count only against the entity cap, so token-level BIO output for a 100 KB transcript (12,000 entities) is fine. Going over a cap is `invalid-output`, so `onError` decides: throw (default) or skip. Nothing is truncated silently, which would leave the remaining names unmasked.
  - Size limits per span and per `word`: 128 characters and 16 tokens. Anything longer isn't a name and is dropped. A BIO chain stops merging at the limit and starts a new span, so every piece is still masked. Before this limit, a 5,000-word span reached propagation's regex, and V8's "regular expression too large" `SyntaxError` quoted the whole text in its message.
- **Cleanup.** A span that starts or ends inside a word is grown to the whole word, because a sub-word token must not leave the rest of a name visible. Spans are not grown in scripts written without spaces, where the "word" would be the whole run ("我是王小明" for "王小明"). There the offsets are trusted. Then whitespace and punctuation are trimmed from both edges. Only BIO continuations are merged: an `I-`/`E-`/`L-` span directly after a `B-`/`I-` span of the same category, touching it or separated only by spaces or tabs. So `B-PER jordan` + `I-PER ellery` becomes one name with one token. Separate entities are never merged: "Attendees: Ana Ruiz Bo Li" tagged as two names stays two names, and plain `PER` spans next to each other stay apart. The two-letter rule below is applied to each piece before merging (except a single CJK or Thai character, which can start a name) and to the result after, so two one-letter tokens can't add up to a "name".
- **Precision filters.** A span is dropped if it has fewer than two letters (initials, digit runs such as a policy number labelled `PER`). A PERSON span is dropped if every word in it is a field label or stop word from the person detector (`Claimant`, `Dear`). Entities below `minScore` (default **0.7**) are dropped. Entities without a score (spaCy has none) are accepted at confidence 0.8 and aren't subject to `minScore`, so a scoreless model is all-or-nothing, which the docs say. `requireCapitalized` is **off by default**, since lowercase names are the gap this closes. It's there for models that over-fire on lowercase common words.
- **Labels.** The default map is `{ PER: "PERSON", PERSON: "PERSON" }`. Lookup ignores case and a `B-/I-/E-/S-/L-/U-` prefix. Other labels are dropped. A user-supplied `labels` map replaces the default. Every category is validated with `assertValidCategory` when the detector is built, so `LITERAL` and non-UPPER_SNAKE categories are rejected before any text is seen.
- **Locations and organisations are not mapped by default.** `LOC`/`GPE` → `ADDRESS` would mask "Austin" and "I-35", and claims need that context. It would also give the `ADDRESS` category two meanings: a street line from regex and a place name from NER. `ORG` hits employers, body shops and carriers, which are usually needed and rarely identifying. Teams that want them map them to their own categories (`{ PER: "PERSON", GPE: "LOCATION" }`) and choose a policy for each.
- **Sync or async.** If `recognize` is typed as synchronous, `nerDetector` returns a plain `Detector` that works with `mask()`. Otherwise it returns an `AsyncDetector`. At runtime the adapter checks each result for a thenable.
- **Concurrency.** At most `concurrency` (default 4) `recognize` calls that pii-gate is *waiting on* run at once per detector. A request with 40 messages doesn't open 40 connections to an NER service. Precisely: a call that times out frees its slot at the timeout. pii-gate can't cancel a promise. It aborts the `signal` and stops waiting, so if `recognize` ignores the signal, the abandoned call keeps running and a slow service can see more than `concurrency` calls in flight. Pass `signal` to `fetch` or the model runtime. Holding the slot until the abandoned call settles was not chosen: a hung call would then hold its slot forever and starve every later request.

### Interaction with the existing pipeline

NER findings are ordinary findings, labelled `detector: "<name>"` (default `"ner"`). Nothing downstream changes:

- **Overlaps:** longest span wins, then higher confidence, then earlier start. A cued "Maria Gonzalez" found by both regex and NER is masked once. NER's span wins the tie if its score is higher. A shorter NER span ("Maria") loses to the longer regex span.
- **Schema hints** win over any detector span that overlaps them, NER included.
- **Placeholder escaping:** `LITERAL` spans are reserved before detection, so an NER span overlapping `{{PERSON_1}}` in the input is dropped. NER can never produce `LITERAL`.
- **Propagation:** NER findings seed propagation like cued names. A lowercase "jordan ellery" also masks "Jordan Ellery" and "JORDAN ELLERY" (full values match case-insensitively), in the same text or another text of the request. Name parts of a capitalised NER name ("Whitlock's") propagate as for cued names. Parts of a lowercase name don't, because parts only match as written and a lowercase "may" or "bill" is an ordinary word.
- **Policy, blocking and audit:** unchanged. A `PERSON: "block"` policy blocks on an NER-found name before any token is issued, and audit counts include NER findings by category. Context suppression (`context.ts`) applies to the numeric regex detectors and has nothing to do here: NER PERSON spans with no letters are dropped anyway.

### Failure handling

If NER fails, the request has lost the layer someone was relying on, so by default **failure is loud**:

- `onError: "throw"` (default). If `recognize` throws or rejects, times out (`timeoutMs`, which also aborts the `signal` passed to `recognize`), or returns something other than an array, the call rejects with `NerDetectorError { detector, reason: "error" | "timeout" | "invalid-output" }`. That's before any token is issued and before the model is called. `wrapAnthropic` writes its usual single audit row with `error: "NerDetectorError"`.
- `onError: "skip"` continues with the other detectors' findings (regex still runs) for deployments where NER is best-effort.
- `onFailure({ detector, reason, error })` is called in both modes, for metrics and alerting. Exceptions it throws are ignored.
- **No text in errors.** `NerDetectorError` carries the detector name and reason only. It deliberately has no `cause`: errors from model clients and HTTP libraries often quote the request body, and `console.error(err)` prints the cause chain. The raw error goes only to `onFailure`, documented as "may quote the input, don't log as-is". The adapter logs nothing.
- **Oversized values never reach an error message.** A schema hint or custom-detector value too long for a regex (V8 compiles patterns lazily, so this can happen on first use) now fails with a `RangeError` naming only the category and length. Before, the engine's `SyntaxError` quoted the pattern, i.e. the value. Any exception while converting model output (an entity whose getters throw, say) becomes `invalid-output`, and the thrown error isn't passed to `onFailure`.
- A call abandoned on timeout may still reject later. The adapter attaches a handler so that isn't an unhandled rejection. A synchronous throw from one detector while another's promise is pending also becomes a rejection, so `Promise.all` still handles both.

## Consequences

- The documented gap closes for teams that can run an NER model, with no new runtime dependency and no change for anyone else. The README's "needs NER" limitation becomes a how-to.
- **NER sees the unmasked text.** That's inherent: the model has to read the names to find them. It has to run inside the same trust boundary as the application (in-process, or a self-hosted service), not at a third party you'd also need a DPA with. The example says so.
- **Latency moves to the model.** Regex costs well under a millisecond. In-process transformers.js inference on a 2 KB note costs tens of milliseconds, and an HTTP NER call costs a round trip. History is masked again on every turn (ADR 0003), so NER runs on the whole conversation each call. Teams with long conversations should memoize `recognize` themselves, keyed by a hash of the text and scoped like their vault. pii-gate doesn't cache, because a cache keyed by raw text is a second copy of the PII with its own retention.
- **Recall depends on the model, and precision filters cost a little recall.** A two-letter given name ("Al") is kept, but a one-letter initial is not. A name a model scores 0.65 is dropped at the default `minScore`. Both are tunable, and misses are documented rather than handled by loosening the filters.
- **Restoration for propagated lowercase names** follows the existing rule: variants that differ in case share one token and come back in the first-seen spelling. "Jordan Ellery" can be restored as "jordan ellery".
- **Propagation is O(distinct detected values × text length).** Each value is searched for with its own regex. That's fine for requests (tens of values, kilobytes of text). It's noticeable for bulk documents with thousands of NER-found names: about 0.5 s for 2,000 names in 1 MB and about 3.3 s for 8,000 (0.06 s and 0.58 s with `propagate: false`). Those calls run synchronously and block the event loop. A combined alternation or token-index prefilter would be faster, but it changes leftmost-match semantics, and with `/iu` case folding it can't be shown never to miss an occurrence. So it wasn't done. For bulk jobs, split documents or set `propagate: false`, at the cost of uncued repeats that NER itself misses.
- `staticDetector` stays for callers who already have spans, but it's no longer the recommended way to do async NER.

## Not chosen

- **Making `Detector.detect` return `Finding[] | Promise<Finding[]>` and `mask()` async.** That's a breaking change for every caller, and it adds microtasks to the regex path for no benefit to the many users who don't run NER.
- **Bundling a model** (transformers.js plus weights) as an optional entry point. Tens of MB, a runtime dependency, and a model choice the library would then own. The adapter takes any model.
- **`onError: "skip"` as the default.** It's friendlier when the NER service is flaky, but it fails open silently: the request goes out with names that the deployment assumed NER would catch. A visible failure plus an explicit opt-out matches how `block` and `unsupportedContent` behave (ADR 0001).
- **Trusting offsets as given.** It's simpler, but code-point/UTF-16 drift and sub-word spans are common enough that a raw span would mask "jor" and leave "dan" visible.
- **Mapping `LOC`/`GPE` to `ADDRESS` by default.** See above: over-masking places the model needs, and one category with two meanings.
- **Per-entity error reporting** (which entities were dropped and why). Dropped entities are counted nowhere. Reporting them without values would add little, and reporting them with values is what this library never does. The tests cover the drop rules instead.
